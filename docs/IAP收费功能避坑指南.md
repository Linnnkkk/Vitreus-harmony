# IAP 收费功能避坑指南
> 来源：Vitreus（鸿蒙 HarmonyOS 应用）内购功能从零到上架的实战档案
> 读者：即将实现收费功能的 AI / 开发者
> 核心心法：**所有不确定的事必须落到实处——看真机日志、查官方文档、读代码原文。绝不主观臆断。**

---

## 0. 心法（先读这个，比坑本身重要）

1. **官方文档不可全信，真机日志才是唯一事实**。本文档里所有字段名都以真机 hilog 实锤为准，其中多个与华为官方文档不符（文档写的 `expirationDate`，实际返回 `expiresTime`）。
2. **不猜任何 API 字段**。想知道返回结构，先埋 `JSON.stringify(rec)` 全量 dump 日志，真机跑一次再看。猜字段 = 白改一轮 + 用户骂一轮。
3. **每个状态键做"写方审计"**：列出该键的**所有写入点**，逐个检查会不会互相覆盖、会不会在错误时机清值。我们 80% 的诡异 bug（会员突然消失、开关自己亮）都是写入点冲突。
4. **单一事实源**：同一段解析逻辑（如"从购买记录提取到期时间"）只允许存在一份实现，所有调用方共用。两套解析 = 必然不一致 bug。
5. **每轮修复都埋下一层诊断日志**。日志驱动逐层收网，比脑补快十倍。

---

## 1. 华为 IAP 返回数据的形态混乱（最大的坑）

`queryPurchases` / `queryOwnedPurchases` 返回的列表**没有稳定 schema**，以下形态全部真实出现过（真机实锤）：

### 列表字段名
- 外层列表字段 = `purchaseDataList`（不是 purchases/productList）
- **防御写法**：`['purchaseDataList', 'purchaseDatas', 'purchaseData', 'purchases', 'productList'].find(k => Array.isArray(rec[k]))` 逐个探测

### 列表元素三形态混用
1. **裸 productId 字符串**（非消耗型沙盒常见）
2. **JSON 字符串**：列表元素是字符串形态的对象，要 JSON.parse
3. **对象**：`{type, jwsPurchaseOrder}` 或 `{type, jwsSubscriptionStatus}`（关键数据在 JWS 里）

### 处理代码骨架
```
for (const item of rawList) {
  if (typeof item === 'string') {
    try { out.push(JSON.parse(item)); }
    catch { if (是合法productId) out.push({productId: item}); } // 裸串构造成记录
  } else { out.push(item); }
}
```

## 2. JWS 解码坑（订阅状态的真数据都在这）

订阅到期时间、productId 都藏在 `jwsSubscriptionStatus` / `jwsPurchaseOrder`（JWS = header.payload.signature 的 base64url）：

```
1. jws.split('.') 取 parts[1]
2. base64url 转 base64：replace(/-/g,'+').replace(/_/g,'/')，尾部补 '=' 到 4 倍数
3. 解码成 bytes 后逐字节 String.fromCharCode 拼字符串
4. JSON.parse
```

**坑点**：
- **字段真名**：到期时间 = `lastSubscriptionStatus.expiresTime`（官方文档写 expirationDate 是**错的**，实际返回 expiresTime——探测列表把 expiresTime 放首位）
- **productId 不在顶层**：在 `lastSubscriptionStatus.lastPurchaseOrder.productId` 嵌套层
- **数字是字符串形态**：`expiresTime: "1735689600000"`——`typeof === 'number'` 检查会**静默拒收**，必须做字符串到 Number 兼容
- **status 枚举**（在 lastSubscriptionStatus 里）：1=生效中 2=已到期 3=尝试扣费(宽限期) 5=撤销
  - **只认 1/3 贡献权益**。撤销(5)的记录 expiresTime 可能仍是未来值，不过滤 = 白嫖漏洞

## 3. 权益状态机——四个致死 bug 模式

状态键设计：`vipPermanent`(永久布尔) + `vipUntil`(订阅到期时间戳ms) + `vipSubProduct`(当前订阅档)。

### 死法 1：权益被覆盖（"买完就掉"）
grant 订阅分支里无条件 `setOrCreate(PERM_KEY, false)` 会把用户刚恢复的**永久会员**覆盖没了。
**铁律：PERM 只增不减**——任何路径写 false 前必须检查当前值；唯一清除途径 = 感知到官方退款状态时的显式回收。

### 死法 2：restore 空结果清空权益（"会员突然没了"）
华为沙盒机制：**finishPurchase 后订单可能从 queryPurchases 消失**。冷启动 restore 查到空列表，若"如实写入"就清空了本地权益。
**铁律：restore 只增不减**——查到有效权益才写入，空结果不触碰本地状态。订阅到期靠 until 时间戳自然失效。

### 死法 3：restore 覆盖砍权益
华为侧记录回退（如退订年订只剩月订记录）时，直接写入会把本地更长的权益砍短。
**修法：写入与本地取 max**（grant 同语义）。

### 死法 4：兜底逻辑造成无限续命
用 `queryOwnedPurchases`（已废弃的 API，返回"**所有**已订购"含过期记录）做兜底，过期订阅每次冷启动都被复活。
**铁律：兜底只允许永久型**（NONCONSUMABLE once granted，个人开发者可接受退款白嫖风险）；**订阅绝不走 owned 兜底**——expiresTime 真值已可解析。
另：grant 解析失败时的档位兜底要**按档位分周期**（月31/年366——写死 31 天会让包年用户只显示一个月）。

### 补充：三键必须 PersistentStorage.persistProp
否则杀进程全蒸发。注册时机：进程最早点（Ability onCreate）+ 关键页面 aboutToAppear 双保险。

## 4. 时序坑

- **finishPurchase（发货确认）可以后台化**：先发本地权益再 finish，不阻塞用户返回（省 1-2s）。finish 只是华为侧记账。
- **购买返回后别急着跳页**：权益已写本地可立即返回，但 toast 要留够时间（800ms 较舒适）。
- **沙盒"时光机"**：沙盒订阅自动续期 6 次（1月=5分钟），恢复购买再+1期。看到"剩 411 天"不是 bug 不用修。
- **沙盒订单时隐时现是常态**：所以才有死法 2/4 的兜底设计。

## 5. 错误码与用户体验

| 错误码 | 含义 | 正确处理 |
|---|---|---|
| 100186 | 用户主动取消收银台 | **静默**（不弹错误 toast）|
| 1001860004 | 已有生效订阅再买订阅 | 人话提示："请先在华为订阅管理取消当前订阅"，别显示"频繁" |
| queryEnvironmentStatus 失败 | 账号未登录/服务未开通/签名问题 | 透出到 UI 帮定位（"真机华为账号已登录？AGC 沙盒已添加该账号？"）|

**商品列表空兜底**：沙盒下 queryProducts 可能查不到草稿商品，但 createPurchase 可直接购买（官方问答实锤）。仅"查询成功且零错误"时用本地写死的 AGC 真实价兜底展示；环境错误时走失败提示块。

## 6. UI 防线（购买页）

- **双防线**：置灰矩阵（响应式，状态键变化全页重算）+ buy() 代码守卫（防时序窗口/选中态残留）。两道逻辑必须**完全一致**。
- **置灰规则**：永久在手，三档全灰只显示已拥有；生效订阅中，月/年灰，永久可买。
- **默认选中**高价值档（锚定效应）。
- **@StorageProp 响应式三键**替代手动 @State 刷新——权益变化自动传导 UI。
- **格式雷**：emoji 不要用（一眼 AI 廉价感）；"最划算"式标签用户会嫌 low；Radio 圆点有表单感，选中态用边框/渐变表达更高级。

## 7. 门禁安全（收费功能最大的安全坑）

**UI 层的会员判断挡不住协议直发**。

我们的真实漏洞：伺服器管理页的开关有 `isVip()` 门禁，但悬浮球面板（WebView 注入的 JS 面板）的三个开启分支没有——面板 JS 的 vip 分支只是 UI 展示，用户/攻击者可以直接发内部协议（`vitreus://srv-toggle`）绕过。而凭证是持久键，订阅过期后凭证残留，面板照样能开收费功能 = 白嫖。

**铁律：每一个"开启收费功能"的执行点（不管从哪个入口触发）都必须在逻辑层自证 isVip()**。UI 只负责展示，不负责安全。

## 8. 调试方法论（照这个流程收网）

1. **全量 dump 探针先行**：每个解析环节 `hilog(JSON.stringify(rec).slice(0, 400))`，先看真机返回的真实形态再写解析。
2. **写方审计**：bug 出现时，grep 该状态键的所有写入点，逐个问"谁在什么时机写了什么"——状态鬼魅 bug 全是这么破的。
3. **回读验证**：权益写入后立刻回读并打日志（`after-read: perm=... until=...`），区分 解析失败/写入失败/持久化未生效。
4. **沙盒账号准备**：AGC 后台添加沙盒测试账号，真机登录该账号。
5. **每轮修复埋下一层诊断**：当前 bug 修好时，顺手埋下一个可疑点的 dump 日志。
6. **构建结果不可全信**：MCP/CI 构建报 ok 可能是增量缓存没编到改动文件，真错误以完整构建输出或真机为准。

## 10. 一句话总结

**字段靠日志实锤、状态靠写方审计、解析靠单一事实源、门禁靠逻辑层自证、兜底只给永久型。**
坑不可怕，可怕的是没看到真机日志就开始猜。
